# 日常协作：一次工作会话的标准流程

适用于已经按 `project-onboarding` 上线、根目录有 `AGENTS.md` 的项目。
如果项目还没有 `AGENTS.md`，先停下，提醒用户先运行 `project-onboarding`。

## 开始

1. **同步最新代码**
   ```bash
   git checkout main
   git pull
   ```
   有未提交的改动时，先停下问用户怎么处理，不要擅自丢弃或覆盖。

2. **读上下文**（按顺序）：`AGENTS.md` → `docs/PROGRESS.md` → `docs/ARCHITECTURE.md` → `docs/DECISIONS.md`

3. **确认任务**：用一两句话复述你理解的任务和打算改动的范围。如果任务和 `DECISIONS.md` 里的决定冲突，先问用户。

4. **看有没有被退回的 PR**：`docs/PROGRESS.md` 的待办里如果登记了你（同一工具名）之前被退回的 PR，先按 PR 里的审查意见改完它，再做新任务。

5. **开分支**
   ```bash
   git checkout -b <工具名>/<任务简述>
   ```
   工具名用你自己的名字：`codex`、`cursor`、`claude`、`grok` 等。
   新任务依赖还没合并的分支时，从那个分支开新分支，并在 PR 说明里写明依赖。

## 进行中

- 只改与任务相关的文件。
- 小步提交，每次提交说明写清楚做了什么。
- 发现任务比预想的大，或者需要改动约定之外的模块，先停下问用户。

## 结束

1. **验证**：运行 `AGENTS.md` 里的测试和检查命令，确认通过。没法通过时，在交接记录里如实写明。
2. **写交接**：在 `docs/PROGRESS.md` 的"工作记录"最上方追加一条：
   ```markdown
   ### YYYY-MM-DD · <工具名> · <分支名>
   - **完成**：
   - **未完成**：
   - **注意 / 坑**：
   ```
   同时更新"当前状态""待办""已知问题"。
3. **记决策**：做了重要的设计取舍，就在 `docs/DECISIONS.md` 加一行。
4. **提交、推送、创建 PR**
   ```bash
   git add .
   git status        # 确认没有密钥、大文件、AI 缓存
   git commit -m "<类型>: <说明>"
   git push -u origin <分支名>
   gh pr create --fill
   ```
   PR 说明里写清楚：做的是哪个任务、怎么验证的、哪些没验证、依赖哪个未合并的分支（如果有）。
   不能创建 PR 时只推送分支也可以，审查任务会扫描未合并的分支。
5. **不要自己合并到 `main`，也不用等用户。** 定时运行的 Claude 审查任务负责审查和合并：
   - 通过：它合并 PR。
   - 没通过：它在 PR 里写明要改什么，并在 `docs/PROGRESS.md` 的待办里登记。下一次会话（你或别的 AI）按意见修改后推送到同一分支。
   - 需要用户做决定的事（例如项目文档里写明的决策关口）：它会通知用户，不替用户决定。
6. **不要强制推送，不要改写已推送的历史。**

## 汇报

结束时用中文简短告诉用户：分支名和 PR 链接、做了什么、测试结果、需要用户决定或处理的事。
